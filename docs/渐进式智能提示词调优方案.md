## 1. 设计哲学：为什么不是"三层/四层/五层/扁平"

Claude Code 的 Skill 树本质是 **「一个极小的路由表（ROOT.md）+ 按需加载的叶子（leaf SKILL.md）」**。它没有把知识切成均匀的 N 层，而是：

- **路由表极简且唯一**（不是一层，是入口）；
- **内容按"领域"自包含成包**（每个包自己携带所需的一切，互不嵌套成层）；
- **装载是惰性的**（用哪个加载哪个，不用的不进上下文）。

本方案据此定义为：

```
                    ┌─────────────────────────┐
                    │  prompt_index（极简索引） │  ← 全局唯一入口，固定极小体积
                    └───────────┬─────────────┘
        ┌──────────────┬────────┴────────┬───────────────┐
        ▼              ▼                 ▼               ▼
  ┌──────────┐  ┌─────────────┐  ┌──────────────┐  ┌──────────────┐
  │ domain_   │  │ domain_      │  │ knowledge_    │  │ execution_    │
  │ component │  │ wiring       │  │ spacing(叶)   │  │ react(叶)     │
  │ (领域包)  │  │ (领域包)     │  │ ...           │  │ ...           │
  └──────────┘  └─────────────┘  └──────────────┘  └──────────────┘
```

- **这不是"层"**：索引不向上级汇报，领域包之间平等、互不直接嵌套；AI 从索引跳到某个包后即获得该包内全部所需信息，无需再逐层下钻。
- **这不是"扁平"**：扁平意味着 13+ 条平铺、首屏全量注入；本方案首屏只有 `prompt_index` 一个极简表。
- **符合渐进式**：索引（最小）→ 领域包（按需，含场景流程+关联函数白名单）→ 知识叶/执行叶（包内细读）。

## 2. 提示词重组（mcp/prompts.js）：由 13 条重构为「1+5+知识叶+执行叶」

> 原 13 条 = `system_message`(1) + `workflow_*`(5) + `business_rules_*`(5) + `execution_*`(3)
> 重组后 **不追求条数一致**，按"是否需首屏加载 / 是否场景绑定 / 是否纯知识 / 是否执行策略"重新归类。

### 2.1 `prompt_index`（替代原 `system_message` 的长枚举，全局唯一入口）
- **保留**：角色定位（10 年嘉立创 EDA 专家）、全局铁律（按需 getPrompt、禁止字符串匹配工作流*、每节点 checkpoint 自检、规则框架内可创新）、函数两大池说明。
- **移除**：原 `system_message` 中罗列的 13 个 name 细节枚举（这是焦点稀释根因）。
- **新增**：一张极简「领域 → 包名」映射表，例如：

  ```
  需求分析      → domain_requirement
  元件设计/放置 → domain_component
  布线设计      → domain_wiring
  验证优化      → domain_validation
  选择交互      → domain_selection
  间距/布局/布线规则/工具要求/碰撞 → knowledge_*（知识叶，按需）
  执行模式      → execution_*（执行叶，按需）
  ```
- **新增**：函数检索指引——明示通过 `listTools({domain})` 取场景相关函数子集、通过 `searchTools({keywords})` 语义检索；并说明"精选函数(curatedTools)"与"EDA函数(eda.*)"两大来源。

### 2.2 五个「领域包」（domain_*，原 `workflow_*` 升级）
每条 domain 包**自包含**：场景流程节点序列 + 每节点关联函数白名单（精选+EDA，带优先级）+ 该场景直接引用的知识叶提示。条数定为 **5 个 domain 包**，与原 5 个工作流一一对应以降低迁移风险，内部结构从"泛化流程"升级为"自包含领域包"：

- `domain_requirement`（原 workflow_requirement_analysis）
- `domain_component`（原 workflow_component_design）
- `domain_wiring`（原 workflow_wiring_design）
- `domain_validation`（原 workflow_validation_optimization）
- `domain_selection`（原 workflow_selection_interaction）

**每个 domain 包内部结构（自包含，不再依赖外部"层"）**：
```
name: domain_component
description: 元件设计领域包（放置/布局/边界/碰撞）
scenario: component_design           // 供 listTools({scenario}) 过滤
associated_functions:               // 函数白名单（强化关联）
  - { tool: 'sch_PrimitiveComponent$create', source: 'curated', priority: 'high', at: 'component_placement' }
  - { tool: 'getCanvasSize',            source: 'curated', priority: 'high', at: 'layout_planning' }
  - { tool: 'calculateComponentBounds', source: 'curated', priority: 'mid',  at: 'collision_detection' }
  - { tool: 'eda.sch_PrimitiveWire.getAll', source: 'native', priority: 'mid', at: 'collision_detection' }
knowledge_refs: ['knowledge_spacing','knowledge_collision']  // 本包常用知识叶
body: |
  （原 workflow_component_design 正文完整保留，节点序列与检查点不删减）
  （节点「推荐工具」改写为精确函数名 + priority 标注）
```

### 2.3 知识叶（knowledge_*，原 `business_rules_*` 改造）
5 条 `business_rules_*` 保留内容为 **5 个知识叶**，每条 `description` 增加 `semantic_tags`（中文标签，用于相似度匹配），例如：
- `knowledge_spacing` ← business_rules_spacing：`tags:[间距,碰撞,mil,边界计算]`
- `knowledge_layout` ← business_rules_layout：`tags:[布局,功能分组,流向,网络标签]`
- `knowledge_wiring` ← business_rules_wiring：`tags:[布线,A*算法,45°走线,障碍物]`
- `knowledge_tools` ← business_rules_tools：`tags:[调用要求,subPartName,分页,lineType]`
- `knowledge_collision` ← business_rules_collision：`tags:[碰撞,重试,边界矩形]`

### 2.4 执行叶（execution_*，原 `execution_*` 改造）
3 条 `execution_*` 保留为 **3 个执行叶**，同样补 `semantic_tags`：
- `execution_react`：`tags:[推理,行动,试错]`
- `execution_plan`：`tags:[规划,验证,调整]`
- `execution_guidance`：`tags:[按需获取,checkpoint]`（由原 execution_guidance 保留并强化"禁止字符串匹配工作流"原则——见 §4.1 保留说明）

> **内容不大幅精简**：所有原正文（间距数值、A* 算法参数、lineType 枚举等）完整保留，仅结构性增强描述字段与标签。

### 2.5 重组后清单（共 1+5+5+3 = 14 条，条数因"索引独立化"而 +1，非机械对应）
`prompt_index` / `domain_requirement` / `domain_component` / `domain_wiring` / `domain_validation` / `domain_selection` / `knowledge_spacing` / `knowledge_layout` / `knowledge_wiring` / `knowledge_tools` / `knowledge_collision` / `execution_react` / `execution_plan` / `execution_guidance`

## 3. 精选工具重构（mcp/curated-tools/index.js）：函数与 schema 聚合（相似集聚）

### 3.1 问题现状（改造前）
改造前精选工具集中在单个 `index.js` 内，文件布局为：
- **前半部**：所有 `async function xxx(){...}` 实现；
- **后半部**：`window.curatedTools.curatedToolSchemas = [ {name,description,inputSchema}... ]` 与 `window.mcpProtocol.metaToolSchemas`。

同一函数（如 `sch_PrimitiveComponent$create`）的"实现体"与"描述/schema"散落两处，阅读需跳转，违背相似集聚原则。

> 改造后现状：精选工具已按 domain 拆分为 `component.js`（元件域）/ `wiring.js`（布线域）/ `selection.js`（选择与交互域）/ `shared.js`（公共函数）四个子文件，各自声明本域的 `*_SCHEMA` 与实现函数；`index.js` 仅做收集与聚合（`curatedToolSchemas` 由 26 个 `*_SCHEMA` 聚合，实现函数由子文件的全局声明汇总），不再承载任何函数实现。

### 3.2 目标结构：每个函数 = 一个自包含单元
将工具描述清单数组**拆解**，把每条 `{name,description,inputSchema}` **内联回对应函数定义处**，形成"实现 + 元数据"紧邻的聚合单元。为最小改动与兼容 DB 覆盖机制，采用如下落地方式：

```js
// ---- 单元聚合示例：sch_PrimitiveComponent$create ----
const SCH_PRIMITIVE_COMPONENT_CREATE_SCHEMA = {
    name: 'sch_PrimitiveComponent$create',
    description: `在原理图放置单个元件(必须使用设备 uuid,subPartName 必填即便为空字符串)
关联领域: domain_component / 优先级: high / 常用节点: component_placement
参数详见 inputSchema`,
    inputSchema: {
        type: 'object',
        properties: {
            uuid:       { type: 'string', description: '设备 uuid（必填）' },
            libraryUuid:{ type: 'string', description: '库 uuid（必填）' },
            x:          { type: 'number', description: '画布 X 坐标(mil)' },
            y:          { type: 'number', description: '画布 Y 坐标(mil)' },
            subPartName:{ type: 'string', description: '子部件名(必填,可空串)' },
            rotation:   { type: 'number', default: 0 },
            mirror:     { type: 'boolean', default: false },
            addIntoBom: { type: 'boolean', default: true },
            addIntoPcb: { type: 'boolean', default: true },
        },
        required: ['uuid', 'libraryUuid', 'x', 'y', 'subPartName'],
    },
    semantic_tags: ['元件','放置','边界','subPartName'],  // 语义相似度索引
    source: 'curated',
};

async function sch_PrimitiveComponent$create({ uuid, libraryUuid, x, y, subPartName = '', rotation = 0, mirror = false, addIntoBom = true, addIntoPcb = true }) {
    // ... 原实现体不变 ...
}
```

`window.curatedTools.curatedToolSchemas` 改为由这些 `*_SCHEMA` 常量**聚合生成**（如 `curatedToolSchemas: [SCH_PRIMITIVE_COMPONENT_CREATE_SCHEMA, GET_CANVAS_SIZE_SCHEMA, ...]`），保持 `listTools()` 返回格式不变。

### 3.3 聚合带来的直接收益
- 阅读某函数时，实现、描述、schema、语义标签、关联领域**同屏可见**；
- 新增/修改函数只需改一处，不再漏改工具描述清单；
- `semantic_tags` 与 `source`/`domain` 字段内联，为 §4 的匹配增强提供数据基础。

### 3.4 元工具（mcpProtocol）同样处理
`window.mcpProtocol.metaToolSchemas` 的 9 个元工具（callTool/listTools/listResources/readResource/listPrompts/getPrompt/getTool/searchTools/searchResources）同样改为"定义处紧邻元数据"的聚合方式，与精选工具一致。

## 4. 三机制落地（均在两个允许文件内）

### 4.1 保留 `getPrompt` 字符串匹配（用户要求 3）
- `getPrompt({name})` 仍按 `name` 字符串**精确查找** `window.promptList`（mcp/meta-tools.js 中 `getPrompt` 逻辑不变）。
- `execution_guidance` 知识叶中"禁止通过字符串匹配工作流"的原原则**保留并强化表述**：AI 应通过 `prompt_index` 的领域映射表定位包名，再用 `getPrompt({name:'domain_component'})` 精确获取，而非在全文做子串猜测。
- 即：**接口机制（字符串精确匹配）保留；使用引导（不要盲目猜 name）优化**。

### 4.2 分层过滤机制（避免海量数据迷失焦点）
- **`listPrompts` 扩展可选 `{ domain }`**：无参返回 `prompt_index` + 各领域包 name（轻量）；有参返回该 domain 下包内知识叶/执行叶 name 列表。
- **`listTools` 扩展可选 `{ scenario }`**（scenario 取值同 domain 包的 `scenario` 字段）：无参返回元工具 + 全部精选工具（兼容现有）；有参仅返回该场景白名单内函数（精选+EDA），注入量从 ~25 降至 ~8–12。
- 调用链：`getPrompt('prompt_index')` → 识别 domain → `listTools({scenario})` 取子集 → 按需 `getPrompt('domain_*' / 'knowledge_*' / 'execution_*')`。首屏不再全量注入。
- **统一工具入口（callTool 协议壳）**：首屏注入只暴露 `metaToolSchemas` 的 9 个元工具，其中 `callTool` 是唯一工具调用入口——所有精选工具与 EDA 原生函数均经 `callTool({name:'<下层工具名>', arguments:{<工具参数>}})` 中转调度（前端恒以 `name='callTool'` 转发，真实目标工具名在 `arguments.name`，由 `callTool` 内部解析后分发），其余元工具（`listTools`/`getPrompt`/`searchTools` 等）为检索与规则获取入口。

### 4.3 动态权重调整策略（强化函数关联）
- 权重**不引入新字段到 ARK function schema**（避免破坏格式），而是写在 **domain 包提示词正文**的 `associated_functions` 里（`priority: high/mid/low` + `at: 节点名`）。
- 同时在每个函数的 `*_SCHEMA.description` 内补 `used_by` 反向标签（如 `（核心场景:domain_component/placement）`），使 AI 读函数描述即知适用节点。
- AI 处于某节点时，对应 `priority=high` 的函数自然优先，无需在全部工具中模糊决策。

### 4.4 基于条目自描述语义的倒排检索增强
- 复用并增强现有 `searchTools({keywords})`（定义于 `mcp/meta-tools.js`，随 `window.mcpProtocol` 挂载）：除名称/描述包含匹配外，新增对 `*_SCHEMA.semantic_tags` 的**标签相似度打分**，返回 `topK` 最相关函数 + 其 `source`/`domain`。
- **语义归属回归条目自身**：每个提示词（`mcp/prompts.js` 的 `semantic_tags` 字段）与每个函数（`*_SCHEMA.semantic_tags`，经 `curatedToolSchemas` 暴露）自带语义标签，不再维护任何"概念→条目名"的中心登记表。
- 新增 `buildInvertedIndex()`：在查询时由 `window.promptList` 与 `window.curatedTools.curatedToolSchemas` **实时聚合**"标签 → 条目名"倒排索引（提示词归 prompts 桶、函数归 tools 桶，携带 source/domain）；任一来源缺失或标签缺失均以空数组兜底，绝不因数据不全抛错。
- 新增纯同义词别名表 `SEMANTIC_ALIASES`（仅承载中文口语别名→标准标签，绝不出现条目名），与具体条目解耦；增删条目不影响它。
- 新增 `matchLeafTool(query)`（**纯增量**，不影响现有调用）：内部调用 `buildInvertedIndex()` + `queryToTags()`，输入概念串，返回 `{ prompts:[叶name], tools:[{name,source,domain}] }`。**新增/删除提示词或函数时，只要条目自身带 `semantic_tags` 即自动被检索到，无需改动任何代码**——彻底消除中心登记表对增删自由的束缚。

> **实施结论（未落地）**：本节所述 `buildInvertedIndex()` / `SEMANTIC_ALIASES` / `queryToTags` / `matchLeafTool(query)` **均未实施**，当前代码中不存在这些符号。实际落地的是 `searchTools({keywords})` 基于 `semantic_tags` 的标签打分检索（`mcp/meta-tools.js`），语义标签已普遍写入 `mcp/prompts.js` 各提示与精选工具的 `*_SCHEMA`，同样达成"增删条目零代码改动"的目标。

## 5. 接口变更清单（mcp/meta-tools.js 与 mcp/curated-tools/index.js，全部向后兼容）

| 函数/对象 | 变更 | 兼容性 |
|---|---|---|
| `getPrompt(params)` | **不变**（仍按 name 字符串精确匹配） | 完全兼容 |
| `listPrompts()` | 新增可选 `domain` 过滤 | 无参行为不变 |
| `listTools()` | 新增可选 `scenario` 过滤 | 无参行为不变 |
| `searchTools({keywords})` | 增强 `semantic_tags` 相似度打分 + 返回 source/domain | 原 keywords 调用仍可用 |
