# 插件接口改造方案

> 目标：让插件同时兼容「火山方舟 Responses API」与「OpenAI Chat Completions 标准接口」。
> 现状依据：`iframe/ark-api.js` 与 `iframe/ai-chat.js` 代码走查（2026-11-04）。

---

## 一、为什么必须改

插件当前有三条对话通道，其中两条会出问题：

| 通道 | 端点 | 当前状态 |
|---|---|---|
| 私服 | `{私服}/api/ark-chat` | 私服已回归标准协议，返回形状随模型 `protocol` 配置变化，**插件只认 ARK 形状，会再次解析失败** |
| ARK 官网 | `/api/v3/responses` | 火山方舟专用接口，换成标准接口后不兼容 |
| 自定义 | `{自定义}/responses` | 假定对方也是 Responses 协议，接 OpenAI 兼容端点会失败 |

**根因**：`parseAIResponse` 写死了 ARK 的两级类型标记（`item.type === 'message'`、`c.type === 'output_text'`），没有其它协议的解析分支。

---

## 二、改造总览

改造分两层，互不干扰：

```
请求层 ark-api.js          响应层 ai-chat.js
  ├─ 按协议构造请求体         ├─ 自动识别响应形状
  ├─ 按协议转 tools           ├─ 统一取出正文 / 思考 / 工具调用
  └─ 按协议管多轮上下文       └─ 供后续流程使用
```

---

## 三、请求层改造

### 3.1 协议枚举

新增一个协议概念，与私服的模型配置保持一致：

```
'ark'       火山方舟 Responses API
'openai'    OpenAI Chat Completions
'anthropic' Anthropic Messages
```

### 3.2 多轮上下文：最大的差异点

这是改造的核心难点，三种协议机制完全不同：

| 协议 | 上下文机制 | 客户端要做的事 |
|---|---|---|
| ARK | 服务端有状态，`previous_response_id` | 只发最后一条 |
| OpenAI | 无状态 | **每次发完整 messages 数组** |
| Anthropic | 无状态 | 同上 |

**改造要点**：

1. ARK 模式保持现状，继续用 `previous_response_id`；
2. 标准模式必须把完整历史塞进 `messages`，请求体随轮数增长；
3. 历史长度需要截断（建议保留最近 20 轮），否则长对话会超出上下文上限；
4. 工具调用轮的处理不同：ARK 用 `previous_response_id` 续接，标准模式要把 `assistant` 的工具调用和 `tool` 结果都放进 `messages`。

### 3.3 请求体结构对照

| 字段 | ARK Responses | OpenAI Chat Completions |
|---|---|---|
| 消息数组 | `input: [{role, content}]` | `messages: [{role, content}]` |
| 模型 | `model` | `model` |
| 工具 | `tools: [{type:'function', name, description, parameters}]` | `tools: [{type:'function', function:{name, description, parameters}}]` |
| 温度 | `temperature` | `temperature` |
| 状态存储 | `store: true` | 无 |
| 缓存 | `caching: {type:'enabled'}` | 无 |
| 续接 | `previous_response_id` | 无 |

**工具格式嵌套差一层**，是最容易写错的地方。

### 3.4 三处请求函数的去重

`callArkChat` 与 `callCustomChat` 除地址、密钥、模型外完全一致。改造时合并为：

```
requestChat(protocol, {baseUrl, apiKey, model, history, previousResponseId, tools, signal})
```

`callPrivateChat` 保持独立（走私服，由私服决定协议），但它也需要按返回形状解析，所以响应层要共用。

## 四、响应层改造

### 4.1 自动识别形状

不改用配置约定，直接看响应里有什么：

| 特征字段 | 协议 |
|---|---|
| 有 `choices` 数组 | OpenAI |
| 有 `output` 数组 | ARK |
| 有 `content` 数组且 `type === 'message'` | Anthropic |

### 4.2 统一提取

把 `parseAIResponse` 拆成三个小函数，各管一种形状，外层按特征分发：

| 提取项 | OpenAI | ARK | Anthropic |
|---|---|---|---|
| 正文 | `choices[0].message.content` | `output[0].content[0].text` | `content[0].text` |
| 思考 | `choices[0].message.reasoning_content` | `output` 里 `type==='reasoning'` 项 | `content` 里 `type==='thinking'` 项 |
| 工具调用 | `choices[0].message.tool_calls` | `output` 里 `type==='function_call'` 项 | `content` 里 `type==='tool_use'` 项 |

### 4.3 兜底文案保留

三项都取不到时才显示「没有收到有效的回复」，并把原始响应写进日志面板，便于排查。

## 六、实施顺序建议

改造要保证每一步都能跑，不能中途全部瘫痪：

1. **先做响应层自适应**：三种形状都能解析，这一步不改变任何请求行为，风险最低，做完立刻能兼容私服已回归的标准格式；
2. **再做工具格式转换**：请求层按协议转 tools，此时仍走原端点；
3. **然后做端点切换**：把 ARK 通道切到标准端点；
4. **最后做上下文改造**：标准模式改为携带完整历史，这一步改动最大，放最后；
5. 全程保留 ARK 通道可用，作为回退。

## 七点五、2026-11-04 实测反馈

配置 deepseek 模型经私服调用 `/api/ark-chat` 时，插件提示「AI 返回的响应格式不正确」。

**已核实的部分**：`ai-chat.js` 的 `parseAIResponse` 三协议分支齐备（`choices` / `content+type=message` / `output`），
该提示文案全仓库仅一处来源（`ai-chat.js` 第 537 行），触发条件是传入的响应不是对象。
故失败点在私服返回内容本身，不在插件的形状判断。

**本文档第 5 项「响应解析按形状分发」确已实现**，但端到端未通过，不构成改造完成。

**待改进**：该提示未附带任何原始响应片段，无法据此定位。建议在解析失败时把响应类型与
前 200 字符写入日志面板，并保留「原始响应」入口，便于排查私服侧问题。

---

## 八、注意事项

- 插件是嘉立创 EDA 扩展包，改完必须 `npm run build` 重新打包分发，无法热更新；
- 改动期间私服不受影响，两条线独立；
- 标准模式的历史数组建议在内存中维护，不落 localStorage，避免隐私与体积问题。
